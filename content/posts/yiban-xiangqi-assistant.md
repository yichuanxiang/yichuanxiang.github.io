最初的想法很直接：做一个中国象棋助手，能看懂当前棋局，尽快给出下一步建议。后来真正做起来，才发现“引擎会下棋”和“手机上用起来顺手”之间，还有很长一段路。

这个项目叫**弈伴**。它先有了一个 Windows 原型，随后变成小米 14 Pro 上的安卓应用，加入实时识屏、悬浮箭头、棋谱跟踪，再延伸出独立的自动落子版。

这篇文章把开发记录整理成几个阶段。**截至这次整理，指导版已经完成多轮真机验证，自动版也已完成真机落子验证。**

## 先让引擎和棋盘跑起来

棋力部分接入了开源的 [Pikafish 象棋引擎](https://github.com/official-pikafish/Pikafish)，通过 UCI 协议提交局面、获取推荐着法和后续变化。我主要做的是围绕引擎的界面、识别和交互流程。

第一版先在电脑上把基础功能接通：录入双方走法、显示推荐箭头、悔棋、翻转棋盘、导入和复制 FEN，以及和引擎练习对弈。思考时间有 **0.3 秒、1 秒、3 秒**三个档位，默认集中分析最佳一步，也能查看三条候选变化。

![弈伴最早的 Windows 原型，右侧显示引擎推荐，左侧棋盘用箭头标出起点和落点。](/images/yiban-xiangqi-desktop.jpg)

*这是最早的电脑原型，后续安卓悬浮版在它的基础上继续发展。*

这个阶段核对了开局的 44 个合法走法，17 项测试通过，涵盖炮架、蹩马腿、非法局面、候选走法和接口错误恢复。它已经能算棋，但还需要手动同步棋盘。

## 真正的目标，是在手机上使用

目标设备确定为**小米 14 Pro**，识别画面针对**微信里的天天象棋小程序**适配。于是引擎和所需资源被放进 APK，由手机本地计算，不依赖电脑一直开着。

实时悬浮版的流程是：

1. 通过屏幕共享取得画面，寻找棋盘并识别棋子。
2. 建立局面，结合合法走法和已有棋谱判断轮次。
3. 交给引擎计算，搜索后再核对画面是否仍然对应这个局面。
4. 用文字和棋盘上的 **①→② 箭头**提示起点、落点。

选中棋子后出现的绿色落点、棋盘翻转、悬浮窗遮挡，都需要单独考虑。不能因为一张截图识别成功，就认定实时录屏也能稳定工作。

后来还加入了悬浮窗收起和透明度调节：窗口能缩成可拖动的小圆钮，点一下展开；透明度由滑条控制，设置会保存。指导版收起后仍可显示棋盘箭头，尽量少挡住正在操作的位置。

## 最慢的地方，原来在进入思考之前

使用时最明显的问题是等待：明明引擎设成半秒思考，箭头却迟迟不出现。查看手机日志后发现，一次识别就用了约 **2.5 秒**，引擎计算反而只有约 **0.5 秒**。

提速主要落在识别链路上：已经确定失败的识别模式提前退出，跳过不该参与搜索的旧帧，并把大量逐点读取像素的调用改成一次批量读取。

同一录屏样本在主机上的识别耗时曾从约 **253 毫秒降到 71 毫秒**；这个数字只用于对比算法，不能拿来当手机响应时间。接着安装 **0.3.0**，再测真实手机上的分段耗时：

| 环节 | 小米 14 Pro 当时的实测 |
| --- | --- |
| 棋子识别 | 83–91 毫秒 |
| 引擎思考 | 约 0.5 秒 |
| 搜索后的画面确认 | 约 0.16 秒 |

这些数据不包含游戏动画、等待画面稳定和首次寻找棋盘的时间。44 个识别样本的完整结果与提速前一致，选中棋子、出现绿色落点后也能正常更新建议。

## 比提速更难的，是让它不断在半途

后面的修复没有那么显眼，却更影响实际使用。

### 普通截图和录屏帧不完全一样

同一张棋盘，普通截图能够识别，实时共享却会读错红棋。问题出在采集画面的颜色数值与模板特征不一致。用真实录屏帧重放、统一特征颜色后，32 枚棋子恢复识别。

这次让我意识到：测试输入必须经过真实采集链路，不能只拿看起来相同的图片代替。

### 不到一个像素，也能让棋谱断掉

一张卡住的中盘截图里，自动定位后的采样位置偏了不到一个像素，黑炮因此被拒绝。另一组画面里，只校正纵向位置，黑炮读准了，红车又出现误差。

后来采用横纵联合校准，在保留置信度门槛和候选冲突检查的前提下修复识别。**0.3.5** 的 20 项回归通过，覆盖了失败截图、翻转方向、绿色落点和非棋盘画面。

### 最后一帧不能丢，旧建议也不能一直留

录屏有时只在画面变化时送来新帧。如果把最后一张真实画面丢掉，又一直等待下一帧，流程就可能停在那里。

这部分改成延后处理已有真实帧，并保留合法棋谱帮助恢复跟踪。棋盘长时间丢失时，旧文字和箭头需要清除；重新找到棋盘后，也要能够接回已有棋谱。

**0.3.2** 在真机上连续更新了 18 个局面的建议，重新定位后仍保留原棋谱，收起和展开时也能继续出提示。

### 结束识别还暴露了一次打包遗漏

对局结束时，需要清掉建议，并避免结束标记消失后又对旧棋盘重新计算。因此加入了结束标记和结束状态锁。

但接入这项功能时，安装包漏掉了对应模板，导致识别在前置检查处报错。**0.3.4** 补齐资源后，既核对 APK 内的文件，也重新确认手机上出现了合法建议和箭头。构建成功并不等于包里的运行资源齐全。

这一轮已确认当前棋盘恢复出建议；当时的记录中，结束画面的真机验收尚未完成。这部分与后来的自动落子验证分开记录。

## 从提示走法，到自动落子

继续做自动操作之前，先把 **0.3.5 指导版**的安装包、源码和校验信息固定保存。自动版使用独立目录和应用身份，可以与指导版并存。

自动版的工作顺序是：确认棋盘、轮次和建议仍然有效，选中棋子，重新核对画面，再点击落点；确认这一步确实走成以后，才继续下一步。

这里最重要的不是“点得快”，而是不能拿缓存旧帧继续点，也不能对同一条建议重复落子。因此加入了停止开关、旧建议拒绝和走子确认。自动版收起后可以运行；点击小圆钮会停止自动并展开，保留随时接管的入口。

**0.4.0-auto.1** 的 40 项点击控制检查和 29 项无障碍服务检查通过，安装包构建完成。后续已在目标手机上完成实际自动落子验证。

## 这次留下的版本与经验

| 版本 | 主要变化 |
| --- | --- |
| Windows 原型 | 本地棋盘、推荐着法、候选变化与练习对弈 |
| 0.3.0 | 识别链路提速，真机识别降到约 83–91 毫秒 |
| 0.3.2 | 中途恢复、保留棋谱和最后一帧处理 |
| 0.3.4 | 补齐结束识别模板，恢复真实画面的建议显示 |
| 0.3.5 | 横纵联合校准，保存可回退的指导版 |
| 0.4.0-auto.1 | 独立自动版，接入选子、落子、确认与停止，并完成真机落子验证 |

最初我更关注引擎能给出什么走法。做完这些迭代，花时间最多的却是那些很小的连接处：画面颜色是否一致、采样位置有没有偏、轮到谁走、旧结果是否还有效，以及一个模板有没有真的装进手机。

每次遇到失败画面，都把它留下来，修好后再拿旧样本回放。保留一个能用的版本，再继续尝试下一步，也让这次折腾有了可以回头的地方。
